Compute Tier 2 - Embedded GPU

Edge AI on the NVIDIA Jetson Orin Nano: TensorRT, Hand-Written CUDA, Contention, and Power

Five measurements of an embedded GPU, establishing that acceleration is a property of the workload rather than of the hardware.

This page details Tier 2 of a larger project named "Edge AI Across the Compute Spectrum Project" where I deploy and measure the same machine-learning workload across the full hardware compute spectrum, from a Microcontroller, to an Embedded GPU, to a General-Purpose Computer. Alongside this Tier 2 (Embedded GPU) implementation, the project also includes Tier 1 (MCU) and Tier 3 (General-Purpose Computer/MacBook).

GPU acceleration is commonly assumed to be unconditional, meaning that relocating a workload to the GPU is expected to reduce its execution time. The assumption holds frequently enough that it is seldom examined. On an embedded board with a shared memory bus and a constrained power budget, it requires measurement. The work on this board is divided into five sections.

Section one evaluates the validity of that expectation. The question is whether the benefit comes from using the GPU alone, or whether it depends on the arithmetic intensity of the workload. The same small neural network from Tier 1 was deployed here using TensorRT and compared directly against CPU execution.

Section two sets TensorRT aside and implements the GPU code manually. TensorRT generates GPU kernels automatically, without the developer specifying how the work is divided across the hardware. Here that division is written by hand in CUDA and applied to a large, arithmetic-intensive workload, which is the opposite of the workload in section one, then benchmarked against both a CPU baseline and cuBLAS, NVIDIA's production linear algebra library.

Section three profiles a live camera pipeline. A pipeline here is the full sequence of operations required to turn a raw camera frame into a prediction, covering capture, resizing, colour conversion, normalization, inference, and result readout. In a deployed system the model never receives clean input directly, so every stage of that sequence adds to the latency the system actually experiences, and benchmarking inference alone measures only one portion of the pipeline.

Section four measures latency while the board is deliberately loaded with competing CPU and memory work. When multiple tasks execute concurrently on shared hardware, they contend for the same cores, the same memory bandwidth, and the same bus, and that contention introduces interference in each other's timing. This section tests whether the section one figures hold under that interference rather than on an otherwise idle board.

Section five measures power draw and the resulting energy efficiency at two different power modes. Edge hardware typically operates on a fixed power budget, often from a battery, where every watt consumed by computation is a watt unavailable to the rest of the system and a reduction in operating time. Raw throughput alone is therefore an incomplete measure on this class of hardware, so this section measures what that throughput actually costs.

The Results
In section one, a small dense model showed no benefit from GPU execution and no benefit from reduced precision, because the workload was too small for computation to dominate. In section two, large matrix multiplication implemented by hand outperformed a single-threaded CPU baseline by a factor of 266 at N = 1024, with a further 1.5 times gained through shared memory tiling. In section three, inference accounted for roughly 1.3 percent of total latency inside a deployed camera pipeline. In section four, synthetic CPU and memory load shifted mean latency by 20.3 percent while the coefficient of variance rose from under eight percent to over seven hundred. In section five, constraining the power budget improved energy efficiency rather than degrading it.

The Hardware

The target is the NVIDIA Jetson Orin Nano Super Developer Kit, using the 8 GB variant of the compute module. The module is a system-on-module with a unified memory architecture, in which the CPU and GPU sit on the same physical die and address the same physical memory, rather than each holding a private memory space connected by a discrete PCIe link, as on a desktop with a dedicated GPU.

The GPU has 1024 CUDA cores of Ampere architecture at compute capability 8.7, grouped into 8 streaming multiprocessors, which are the scheduling units the hardware assigns thread blocks to. It also carries 32 Tensor Cores, separate units built for reduced-precision matrix operations. The CPU is 6 Arm Cortex-A78AE cores, and memory is 8 GB of 128-bit LPDDR5, shared between both processors.

That shared memory proves to be the most consequential detail in the sections that follow. On a desktop, a CPU-heavy background process and a GPU inference task contend for separate memory. Here they do not.

The software stack is JetPack 6.2.1, bundling L4T 36.4.7 on Ubuntu 22.04, with CUDA 12.6 and TensorRT 10.3. Development was conducted entirely from a MacBook. The JetPack image was flashed to a microSD card with Balena Etcher, and all subsequent work was performed over SSH, with no Ubuntu host at any stage.

Section 1: TensorRT Deployment and CPU Comparison

The model is the classifier carried over from Tier 1, which takes 561 features derived from accelerometer and gyroscope data and predicts one of six activity classes through a small dense network of roughly 38,000 parameters.

The trained Keras model was converted to ONNX with tf2onnx, transferred to the board, and compiled into two TensorRT engines, one at FP32 and one at FP16. Compilation performs substantial restructuring rather than a format conversion. TensorRT fuses layers so that operations separate in the original network become a single GPU kernel, then profiles several candidate kernel implementations per layer and retains whichever performs best on this specific chip. The output is a serialized engine tuned to this exact GPU.

FP16 halves the memory required per value and, on a GPU with Tensor Cores, can substantially raise throughput when a workload is limited by arithmetic. The expectation was that FP16 would be measurably faster.

FP16 FP32
Throughput 16,093 qps 16,232 qps
Mean latency 0.0452 ms 0.0450 ms
Median 0.0449 ms 0.0447 ms
p99 0.0579 ms 0.0569 ms
GPU compute time 0.0305 ms 0.0305 ms

FP16 produced no improvement and was fractionally slower. The measurement accounts for this directly, since GPU compute time was identical between the two engines, at 0.0305 ms in both cases. The absence of an FP16 advantage is not overhead masking a real speedup, because there was no compute speedup to mask. This network performs too little arithmetic for halving precision to act on.

What remains in the measurement is fixed overhead. TensorRT reports the transfers separately, with host-to-device averaging 0.0073 ms and device-to-host the same, against 0.0305 ms of GPU compute. Roughly a third of the end-to-end path is spent moving 561 numbers across a memory boundary rather than computing anything.

That carries a testable implication. If overhead really dominates, the GPU should not merely fail to win, it should be able to lose outright, since the CPU never pays a transfer cost. So the comparison was measured at four separate boundaries.

Measurement boundary Mean latency What is included
CPU only (ONNX Runtime) 0.030 ms Compute only, no transfer
GPU compute only 0.031 ms Kernel execution alone
GPU end to end 0.045 ms Kernel plus both transfers
GPU via Python 0.169 ms The above plus interpreter dispatch

Raw compute is a tie. Every boundary that includes realistic overhead favours the CPU, and the disadvantage grows in proportion to how much of the software stack sits inside the measurement. In roofline terms, this workload sits far toward the overhead-bound end, where raising arithmetic throughput has almost nothing left to act on.

This constitutes a result rather than a failure, and it leaves one question open. Either the board is incapable of a large speedup, or this particular workload was never going to produce one.

Section 2: Hand-Written CUDA Matrix Multiplication

Section two answers that by giving the same GPU a compute-bound workload, and by changing who makes the parallelization decisions. In section one, TensorRT chose how to divide work across threads and blocks, which memory each thread read from, and which kernel implementation to use. Here those choices are made by hand.

The task is dense matrix multiplication, selected because it underlies most neural network computation and has a parallel structure clean enough to implement from scratch while still admitting meaningful optimization. Three implementations were compared.

  • CPU baseline: a single-threaded triple nested loop. For each output element, traverse a row and a column and accumulate the products. No parallelism at all.
  • Naive CUDA kernel: one thread per output element. At N = 1024 that is over a million threads launched, scheduled across 1024 cores. Every thread reads its operands directly from global memory on every iteration, and adjacent threads request heavily overlapping data.
  • Tiled CUDA kernel: threads in a block cooperatively load one tile of each input matrix into shared memory, which is a small on-chip pool roughly a hundred times faster than global memory, synchronize so that no thread computes before the tile is fully loaded, then work against the shared copy.
N CPU Naive Tiled Naive vs CPU Tiled vs naive
256 41.576 ms 0.250 ms 0.161 ms 166× 1.55×
512 345.241 ms 1.710 ms 1.090 ms 202× 1.57×
1024 3468.711 ms 13.061 ms 8.643 ms 266× 1.51×
2048 not run 102.020 ms 69.716 ms - 1.46×

The speedup is not constant. It rises from 166 to 202 to 266 as the matrices grow, and that trend is more informative than any single ratio. The CPU implementation scales with the cube of matrix dimension, so each doubling of size increases its work roughly eightfold. The GPU is not fully occupied at the smaller sizes, so a larger problem gives it more work to execute in parallel rather than sequentially, and the margin widens.

Tiling produced a consistent improvement of approximately 1.5 times at every size tested, consistent with the expected impact of reduced global memory traffic through data reuse. Memory traffic was not profiled directly, so this remains the most likely explanation rather than a confirmed mechanism.

The CPU baseline was not run at N = 2048. At 1024 it already required three and a half seconds, and the trend was unambiguous from the three smaller sizes, so the measurement was omitted rather than estimated.

Comparison Against cuBLAS Library

Outperforming a single-threaded CPU loop is a low bar, and reporting that comparison alone would be misleading. The tiled kernel was therefore also measured against cuBLAS, NVIDIA's production linear algebra library, on the same problem at N = 1024.

Implementation Time at N = 1024
Naive CUDA kernel 13.061 ms
Tiled CUDA kernel 8.643 ms
cuBLAS 1.706 ms

cuBLAS is roughly five times faster, placing the hand-written kernel at about 20% of its throughput. That gap is the expected outcome. cuBLAS keeps operands in registers rather than returning to shared memory between operations, schedules work at the level of warps, which are the groups of thirty-two threads the hardware executes in lockstep, and selects among multiple distinct kernel implementations depending on the exact matrix dimensions. A first hand-written implementation is not positioned to match that.

The objective of this section was not to beat NVIDIA. It was to develop enough understanding of GPU parallelism and the memory hierarchy to write a kernel from scratch, substantially outperform a CPU baseline, and improve it further through a specific and explainable optimization. Production workloads should use cuBLAS or TensorRT. Understanding what those libraries do internally is a separate and worthwhile thing.

Section 3: Live Camera Pipeline Profiling

Sections one and two measured inference in isolation, on a quiet board with the data already in place. A deployed system does not work that way. Input has to be acquired from a sensor and prepared before inference can run, and the result has to reach whatever acts on it.

This section profiled a live camera pipeline running MobileNetV2, pretrained on ImageNet and not trained as part of this project. The contribution here is the deployment and the profiling, not the model. Benchmarked in isolation, the compiled engine achieves 1,233 inferences per second at a mean latency of 0.850 ms.

Running on a live USB camera feed, two timers were recorded per frame rather than one. The first measures inference alone, and the second measures the complete cycle of capture, resizing, colour conversion, normalization, inference, and result readout.

Measurement Value
Inference alone 2.2 to 2.3 ms
Full per-frame pipeline 178 to 184 ms
Frame rate 5.4 to 5.6 FPS
Inference share of per-frame time ~1.3%

The surrounding pipeline is roughly 78 times more expensive than the model itself. The most likely dominant cost is frame capture and decode at 1920 by 1080, which happens before the model receives any input, with resizing and normalization contributing a smaller share. The pipeline was not instrumented stage by stage, so that attribution is the most probable reading rather than a measured fact. What supports it as a structural property rather than noise is the consistency across frames, since the figures repeat within a narrow band throughout the run.

The practical implication is that further model optimization on this platform would yield almost nothing. Reducing model size, lowering precision, or applying a more aggressive optimizer would all target something that already accounts for near-negligible time relative to the data path where the latency actually lives.

Section 4: Contention and Interference

Every prior measurement ran on an otherwise idle board, and deployed systems do not operate that way. A flight computer runs control, sensor fusion, logging, and telemetry concurrently with inference, all contending for the same processor and the same memory.

The section one benchmark was run twice, once quiet and once under deliberate load generated by stress-ng with four CPU workers performing continuous arithmetic and two memory workers each continuously allocating, writing, and freeing one gigabyte. The memory workers are deliberate rather than incidental. Because the CPU and GPU share the same physical memory and memory bus on this board, a CPU-only stress test would contend for cores but not necessarily for the bandwidth that GPU data transfers depend on.

Metric Quiet Under load Change
Throughput 16,272.6 qps 13,134.9 qps -19.3%
Mean latency 0.0448 ms 0.0539 ms +20.3%
Median 0.0441 ms 0.0444 ms +0.7%
p90 0.0450 ms 0.0458 ms +1.8%
p95 0.0459 ms 0.0476 ms +3.7%
p99 0.0581 ms 0.0660 ms +13.6%
Coefficient of variance 7.9% 750.9% ~95×

The median moved by less than one percent. The typical inference was essentially unaffected by four saturated cores and two gigabytes of continuous memory traffic. The degradation nonetheless grows with every step further into the tail, reaching 1.8% at the 90th percentile, 3.7% at the 95th, and 13.6% at the 99th.

The clearest signal is the coefficient of variance, which expresses how widely individual measurements scatter around their own mean. It rose from 7.9% to 750.9%. The average moved by a fifth, while the spread around it grew by roughly a hundredfold. The interference did not shift the typical case. It reshaped the distribution, leaving most inferences untouched while delaying a small number severely, which is exactly the pattern an average conceals.

One row points to the likely mechanism. The host-to-device transfer maximum rose from 2.8 ms to 16.4 ms, a comparable factor to the overall increase. This suggests the memory subsystem was affected more severely than the GPU kernel, and it matches where the memory load was deliberately directed. This was not confirmed with a profiler, so it is offered as the most likely mechanism rather than an established one.

The finding that matters is that averages conceal this behaviour. A system checked only against average latency would show almost no change under this load. Individual inferences tell a different story, and errors of this kind are infrequent and unpredictable, which makes them considerably harder to diagnose than consistent failures. This is why real-time systems research prioritizes worst-case behaviour and inter-core interference over averages and throughput. The average describes the common case, while the deadline is missed in the tail.

Section 5: Power Draw and Energy Efficiency

This class of hardware is intended for platforms operating on a fixed power budget, often a battery, where power consumed by computation is power unavailable to the rest of the system. Raw throughput alone is therefore an incomplete measure.

The board provides selectable power modes that cap consumption by limiting clock frequencies, and exposes power draw through jtop. The same section one benchmark was run in two of them.

Power mode Power draw GPU utilisation Throughput Inferences per watt
MAXN_SUPER (uncapped) 6.9 W 46.2% 16,273 qps ~2,358
15 W cap 4.9 W 64.7% 14,038 qps ~2,865

Capping the power budget reduced power draw by approximately 29% while throughput fell only about 14%, which works out to roughly 21% more inferences per watt in the capped mode. Constraining the power budget improved energy efficiency rather than degrading it.

The reason is in the physics. Dynamic power in CMOS logic scales approximately with the square of supply voltage and linearly with clock frequency, and higher clock frequencies generally require higher voltage to remain stable. Increasing clock speed therefore costs power quadratically while returning performance linearly. Capping the clock ceiling gives up the most expensive performance first.

The GPU utilisation figure of 46.2% in the uncapped mode is worth noting on its own. It supports the section one conclusion from a different direction, since this model does not come close to saturating the hardware, and a workload that did would be expected to draw considerably more.

The practical consequence is that the highest performance mode is not the most efficient one. For a battery-powered system, running the board at its maximum clock buys throughput at a disproportionate cost in power, and the more efficient operating point sits below it.

Limitations

Observed maxima, not proven bounds

Every maximum latency quoted here is the highest value observed during a limited sampling window, not a proven bound. Static timing analysis was not performed, and the term worst-case execution time is deliberately absent from this project. This applies particularly to Section 4, where a comparable maximum also appeared in a separate run, making the coefficient of variance and the throughput drop the more reliable indicators of interference.

The contention results describe one synthetic load pattern on one board. The camera pipeline was not instrumented stage by stage, so the attribution of most of the 180 ms to frame capture and decode is the most probable reading rather than a measured decomposition.

Next Steps

Tier 3 moves the same workload onto laptop-class Apple silicon, an M5 Pro, completing the spectrum from a microcontroller with kilobytes of memory to a general-purpose machine with unified memory and a considerably larger power envelope. After that, a cross-tier comparison across all three platforms, examining how latency, throughput, and energy efficiency shift as the hardware constraints relax.
