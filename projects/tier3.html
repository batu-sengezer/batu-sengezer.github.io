Compute Tier 3 - General-Purpose Computer

CPU vs GPU vs Neural Engine on Apple M5 Pro (Edge AI Across Compute Spectrum)

Three compute units on one die, and a workload too small for any of them, closing a three-tier spectrum with a cross-tier comparison.

This page details Tier 3 of a larger project named "Edge AI Across the Compute Spectrum Project" where I deploy and measure the same machine-learning workload across the full hardware compute spectrum, from a Microcontroller, to an Embedded GPU, to a General-Purpose Computer. Alongside this Tier 3 (General-Purpose Computer) implementation, the project also includes Tier 1 (MCU) and Tier 2 (Embedded GPU). This page also carries the cross-tier comparison that closes the series.

This tier introduces a third processor to the comparison. The microcontroller in Tier 1 offers a single CPU, and the embedded GPU board in Tier 2 pairs a CPU with a GPU. This chip pairs a CPU and a GPU with a dedicated neural accelerator, all addressing the same pool of memory. The question this tier asks is narrower than the two before it: when a platform offers several kinds of accelerator, does a small model benefit from any of them, and if not, how much work does a single call have to carry before each one begins to pay off? The work on this machine is divided into six sections.

Section one moves the model onto the platform. The classifier was trained in Keras, but reaching the Apple GPU requires PyTorch, so the weights had to be ported and the port had to be verified rather than assumed. Nothing measured afterwards means anything if the network is not the same network.

Section two compares the CPU against the GPU at one sample per call, which is the batch size this application uses in deployment. Human activity recognition produces one feature vector per sampling window, so a single sample is the realistic case rather than a conservative one.

Section three increases the batch size until the GPU overtakes the CPU. Section two establishes that the GPU loses without establishing why, and two explanations remain open at that point. Either the GPU suits this network badly, or a single call carries too little work to justify dispatching it. The two behave differently as the calls grow, which is what makes them separable.

Section four addresses the Neural Engine, the one unit on this chip built specifically for inference. It cannot be reached from PyTorch, only through Core ML, which does not accept instructions about which processor to use so much as permissions, leaving the final decision to its own scheduler.

Section five measures power draw on both execution paths. This machine is not power constrained in the way the two smaller platforms are, but the measurement serves a second purpose here, since the power rails report each compute unit separately and can confirm what the timing data alone cannot.

Section six places all three tiers side by side, comparing latency, throughput, power, and energy efficiency across a microcontroller, an embedded GPU board, and a laptop-class chip running the same classifier.

The Results
In section one, the ported model matched the original to a maximum output difference of zero. In section two, the GPU was 6.5 times slower than the CPU at one sample per call. In section three, the same GPU overtook the CPU at batch 512 and reached 2.31 times by 1024, identifying the workload rather than the hardware as the constraint. In section four, Core ML never engaged the Neural Engine at any setting, confirmed independently by a power rail that read zero throughout. In section five, the CPU accounted for roughly 97 percent of power draw during nominally GPU work. In section six, the M5 Pro proved more energy efficient than both smaller platforms, while the microcontroller retained the absolute power advantage that gates deployment on a battery.

The Hardware

The target is a MacBook Pro carrying the Apple M5 Pro, model identifier Mac17,8. Like the Jetson in Tier 2, it is a system-on-chip with a unified memory architecture, in which the processors sit on the same die and address the same physical memory rather than each holding a private space connected by a discrete link. Unlike the Jetson, it carries a third processor.

The CPU has 18 cores, six of what Apple calls super cores and twelve performance cores, with 24 GB of unified memory shared across every compute unit. The GPU is reached through Metal Performance Shaders, Apple's GPU compute framework, and the Apple Neural Engine through Core ML. The machine runs macOS Tahoe 26.5.1, with Python 3.12 on arm64, PyTorch 2.12.1, coremltools 9.0, and TensorFlow 2.21.0.

Unified memory removes the explicit host-to-device copy that consumed roughly a third of the end-to-end path in Tier 2. It does not remove the cost of dispatching work, and it means the CPU stays involved in anything the GPU runs, which becomes the subject of section five.

Section 1: Porting the Model and Verifying It

The model is the classifier carried through the entire series, taking 561 features derived from accelerometer and gyroscope data and predicting one of six activity classes through three fully connected layers of 38,246 parameters. It was trained in Keras, quantized to INT8 for the microcontroller in Tier 1, and exported to ONNX for TensorRT in Tier 2.

Neither of those paths reaches the Apple GPU. PyTorch's Metal Performance Shaders backend is the supported route to that hardware, so an identical architecture was constructed in PyTorch and the weights transferred layer by layer, transposing each weight matrix because Keras and PyTorch adopt opposite conventions for the orientation of dense layer weights.

A weight transfer of this kind either works completely or fails in ways that are easy to miss, so it was checked rather than assumed. The same input vector was passed through both models and the outputs compared element by element.

The network benchmarked in the sections that follow is numerically the same network deployed in Tiers 1 and 2, not an approximation of it or a retrained equivalent. That is the prerequisite the entire cross-tier comparison rests on.

Section 2: CPU Against GPU at One Sample Per Call

Each configuration was measured over 1,000 timed calls preceded by 50 warmup calls, timed with perf_counter. The GPU measurements required one additional precaution. Metal dispatch is asynchronous, meaning the call returns before the GPU has finished, so each GPU timing is followed by an explicit synchronize before the timer stops. Without it, the measurement reports how long it took to queue the work rather than how long it took to complete.

Backend Mean latency Relative to CPU
PyTorch, CPU 0.0114 ms baseline
PyTorch, GPU via Metal Performance Shaders 0.0740 ms 6.5× slower

The GPU does not merely fail to help. It loses outright, by a wide margin. The explanation is dispatch overhead. Before the GPU performs any arithmetic, the CPU must encode the command, submit it to a queue, and synchronize on the result. This forward pass is three matrix-vector products totalling 38,144 multiply-accumulate operations, which a single CPU core completes in a few microseconds. The fixed cost of engaging the GPU exceeds the cost of the computation being dispatched.

This reproduces the Tier 2 finding on unrelated hardware through an unrelated toolchain, where TensorRT on the Jetson showed no measurable GPU advantage on the same model. Two vendors' accelerators, reached through two different software stacks, independently reach the same conclusion about this workload.

One point is worth stating about how the parallelism was obtained, since neither backend was written by hand. On the CPU, PyTorch distributes the layers across cores through its ATen backend, which is OpenMP backed, selecting thread count and placement itself. On the GPU, moving the tensors to the Metal device delegates kernel selection and thread group sizing to the framework. This is the opposite of the approach in Tier 2 section two, where the CUDA kernels were written directly, and it means these figures characterize the framework's default behaviour on this hardware rather than a parallel implementation designed for it.

As in Tier 2, this is a result rather than a failure, and it leaves the same question open. Either this GPU is poorly suited to this network, or a single sample is too little work to justify dispatching.

Section 3: Batch Size and the Throughput Crossover

Those two explanations behave differently as work per call increases. A structural mismatch would not improve with scale. Dispatch overhead would, because a larger batch spreads that fixed cost across more samples. Batch size here means the number of input samples processed in a single call, and the sweep ran from 1 to 1024 with 200 timed calls at each point on both devices.

Batch CPU throughput GPU throughput GPU relative to CPU
1 88,623 inf/s 12,760 inf/s 0.14×
8 194,038 inf/s 100,247 inf/s 0.52×
32 757,609 inf/s 399,915 inf/s 0.53×
128 2,058,843 inf/s 1,670,192 inf/s 0.81×
512 4,786,137 inf/s 6,086,483 inf/s 1.27×
1024 5,604,063 inf/s 12,968,969 inf/s 2.31×

The deficit narrows monotonically as the batch grows, crossing parity between 128 and 512. That rules out a structural mismatch and confirms dispatch overhead as the constraint.

The behaviour after the crossover is more informative than the crossover itself. Between batch 512 and 1024, CPU throughput increased by roughly 17 percent while GPU throughput increased by roughly 113 percent. The CPU is approaching saturation, with no further cores to bring to bear. The GPU is still filling and had not reached its own limit at the largest batch tested. The figure of 2.31 times is therefore a lower bound rather than a peak, and the sweep terminated because of the range selected rather than because the hardware stopped improving.

One qualification belongs with that number. A batch of 1024 means 1024 sensor readings arriving simultaneously, which a streaming workload does not produce. The measurement describes what the silicon is capable of rather than what this application would request of it. Its value is in locating the boundary, so that a given deployment can be evaluated against it.

Taken together, sections two and three give the central result of this tier. On identical hardware running an identical model, the same GPU is 6.5 times slower at one sample per call and 2.31 times faster at 1024. Nothing about the hardware changed between those two measurements. Only the amount of work per call did.

Section 4: Core ML and the Neural Engine

The Neural Engine is the compute unit designed specifically for inference, and therefore the one most likely to help. It is not reachable from PyTorch, so the model required conversion to Core ML.

Direct conversion from the Keras model was attempted first and failed twice, initially because coremltools could not infer the source framework and then, once that was specified, because the installed Keras version exposes a model object the converter does not recognize. The path that succeeded routes the model through PyTorch and a traced graph before conversion, which is why the pipeline retains a PyTorch stage that would otherwise appear redundant.

Core ML also does not behave the way the API initially suggests. It does not accept an instruction specifying which compute unit to use. It accepts a permission, expressed as a compute unit setting, and its own scheduler then decides what to use within whatever it has been allowed. Measuring the three settings therefore reports what the scheduler chose, not what was requested.

Compute units permitted Mean latency
CPU only 0.0341 ms
CPU and GPU 0.0337 ms
All units, including the Neural Engine 0.0341 ms

The three settings are indistinguishable. Permitting the GPU changed latency by roughly one percent and permitting the Neural Engine by less than that, both inside run-to-run variation, which is consistent with the scheduler having executed the model on the CPU in every case.

Latency alone cannot establish that, and this is where the measurement would ordinarily stop short. Identical timings would also result if the Neural Engine had executed the model and happened to match CPU performance exactly. The two hypotheses are indistinguishable from timing data.

The power measurement in the next section resolves it. Across every sample of every run, including the runs in which the Neural Engine was explicitly permitted, its power rail reported zero milliwatts. A compute unit drawing no power is not executing work. Two independent signals, latency and power draw, agree that the accelerator was available and the scheduler declined to use it.

The most likely explanation is the one established in the previous two sections. The Neural Engine is designed around large convolutional and transformer workloads, and engaging it carries fixed costs in model compilation and dispatch that a three-layer dense network of 38,246 parameters does not repay. Apple's scheduler appears to apply a cost model that reaches the same conclusion the GPU measurements reached independently.

These Core ML latencies also include the cost of crossing from Python into Core ML on every call, which involves dictionary construction and array marshalling. All three figures sit near three times the PyTorch CPU measurement for identical arithmetic, consistent with that overhead being a substantial share of the total at this model scale. The ordering between the rows is meaningful, while the absolute values are an upper bound on true inference cost.

Section 5: Power Draw

Power was sampled with powermetrics at one second intervals, running concurrently with the benchmark in a separate terminal. It reports the CPU, GPU, and Neural Engine rails separately, which is what made the confirmation in the previous section possible.

State CPU rail GPU rail Neural Engine rail Combined
Idle 285 mW 14 mW 0 mW 298 mW
CPU execution 2,459 mW 26 mW 0 mW 2.49 W
GPU execution, batch 1024 8,284 mW 273 mW 0 mW 8.56 W

The Neural Engine column reads zero in every state, which is the independent confirmation section four relies on.

The distribution across the other two rails during GPU execution was not the expected result. The GPU rail rose to 273 mW while the CPU rail rose to 8,284 mW, so the CPU accounted for roughly 97 percent of the power drawn during work that is nominally executing on the GPU. On a unified memory architecture the CPU does not go idle while the GPU computes. It encodes commands, submits them to the queue, synchronizes on results, and manages memory throughout, and in a benchmark loop that submits calls back to back with no other work in between, that overhead becomes the dominant power cost. An application performing other work between inferences would not necessarily show this distribution.

Dividing throughput by combined power gives roughly 35,600 inferences per second per watt on the CPU at batch size one, and roughly 1,515,000 on the GPU at batch 1024. These describe two different operating modes rather than the same task measured twice.

Limitations

Measured means, not proven bounds

All latency figures are measured means on an unpinned, thermally uncontrolled macOS system, not proven bounds, unlike the bare-metal timing in Tier 1 or the pinned clocks in Tier 2, so these figures carry more uncertainty than either.

Only mean latency is reported. Tiers 1 and 2 also reported the tail, standard deviation and observed maximum, and the full percentile distribution respectively, which is where a real-time argument would actually live. That is absent here.

The Neural Engine result lacks a positive control. No accelerator-eligible model was run through the same conversion pipeline, so a faulty dispatch configuration cannot be fully ruled out as the cause. The agreement between the latency and power signals makes that unlikely, but the result remains strongly supported rather than established.

The power figures average a one second sampling interval across thousands of inferences, with phases attributed from timestamps rather than instrumentation, and the idle floor not subtracted. Inputs were randomly generated rather than drawn from the UCI HAR test set, and the Keras-to-PyTorch port was verified numerically, not against classification accuracy.

Latency and throughput rank as expected, improving monotonically as the hardware grows. Energy efficiency does not. The STM32 and the Jetson trade places between the two metrics, with the Jetson ahead on raw throughput and the microcontroller ahead on inferences per watt. That reversal is the most interesting thing in the table.

The Jetson draws 6.9 W to deliver throughput the M5 Pro CPU exceeds five times over at roughly a third of the power, and it ranks last on efficiency of the four columns. This is not a deficiency of the board. Tier 2 measured the same Jetson reaching 266 times a single-threaded CPU baseline on a hand-written CUDA matrix multiplication. The hardware is capable, and this model is too small to occupy it. A board drawing that much power spends most of it staying ready rather than computing, and a workload of 38,144 operations never claims what it is paying for.

The M5 Pro leads on efficiency as well as speed, which corrected an expectation held before measuring. Its CPU delivers roughly 3.7 times more inferences per watt than the microcontroller, and its GPU at large batch roughly 157 times more. Newer silicon, built on a more advanced manufacturing process, performs more work per joule, and architectural simplicity does not compensate for that.

What the STM32 wins is absolute power. Approximately 132 mW against 2.5 W. That is a deployment gate rather than a performance ranking. If a platform's power budget is 200 mW, the laptop chip is unavailable regardless of how efficiently it converts watts into inferences. Efficiency becomes the deciding metric only once the absolute draw is affordable at all, and for a battery-powered sensor node it frequently is not.

On comparing these figures

The STM32 power figure is a datasheet estimate (238 µA/MHz in run mode from Flash, 168 MHz, 3.3 V), not a measurement. The three tiers also measure power at different scopes: the microcontroller only, whole-board input for the Jetson, and chip rails only for the M5 Pro. Precision differs too, INT8 on the microcontroller against FP32 on Apple silicon, and each tier reports latency from its own toolchain. These ratios describe deployed configurations, not hardware held to one common standard.

Conclusions

For this workload specifically, the answer is unambiguous. UCI HAR classifies a 2.56 second window with 50 percent overlap, so a deployed system requires roughly one inference per second. The STM32 delivers 1,270 per second, at 0.79 percent CPU utilisation, on approximately 132 mW. It exceeds the requirement by more than three orders of magnitude on the smallest platform in the series. Nothing above the microcontroller is justified, and the useful question is not which platform is fastest but how much of the microcontroller remains available for everything else the device has to do. At 0.79 percent utilisation, nearly all of it.

The general conclusion is the pattern that repeated on every platform tested. On the STM32 the classifier ran at under one percent CPU utilisation. On the Jetson it showed no measurable GPU advantage and no benefit from reduced precision. On the M5 Pro the GPU lost outright at batch size one and the Neural Engine never engaged at all. Three platforms, three toolchains, three vendors, and the same answer each time.

Accelerators pay off only when a single call carries enough arithmetic to cover the cost of dispatching it. This classifier performs 38,144 multiply-accumulate operations per inference. MobileNetV2, which ran on the Jetson GPU in Tier 2 without any timing instability, performs roughly three hundred million. The threshold sits somewhere between those two figures and was not measured in this project. Below it, the CPU wins on every platform tested and the specialized silicon sits idle.

Section three demonstrates the other route past that threshold. Aggregating enough small calls into a single batch also clears it, which is why the M5 Pro GPU overtakes its own CPU at batch 512. That option is available only to applications that can afford to wait while the samples accumulate, which a streaming sensor workload cannot. A vision model processing many camera frames per second, or a batch job classifying a stored dataset overnight, is the kind of workload that would actually justify the Jetson or the M5 Pro over a microcontroller.

Next Steps

The clearest extension for this tier is a positive control for the Neural Engine, running a model known to be accelerator-eligible through the same conversion pipeline, which is the single change that would most strengthen the section four conclusion. Beyond that, a hand-written OpenMP implementation of the forward pass would replace framework-managed CPU parallelism with an explicit thread decomposition, producing the strong-scaling curve and parallel efficiency figures the framework path conceals, and giving this tier the equivalent of the hand-written CUDA work in Tier 2. Percentile reporting and a contention study matching the Tier 2 methodology would make interference sensitivity a cross-tier axis rather than a single-platform observation.
